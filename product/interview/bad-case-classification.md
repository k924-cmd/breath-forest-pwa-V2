# Bad Case 分类体系 —— 双向语音链路（播报 + 唱歌彩蛋）

> 面试用途：Bad Case 分析题。用本项目「ASR → Speech LLM 判断 → TTS（播报/唱歌）」真实链路的真实踩坑分类，代替空谈"我们会分析 bad case"。
>
> 对应代码：`backend/src/adapters/dashscope-asr.js`（ASR）、`backend/src/conversation/mimo-easter.js`（意图判断编排）、`backend/src/adapters/mimo-tts.js`（TTS）、`backend/src/conversation/assistant-service.js`（synthesizeSpeech）。
> 评测工具：`backend/tools/wer.js`（CER/WER 计算）。

## 1. 为什么 Bad Case 分析是语音 Agent 的刚需

语音链路是**多模型串行**，错误会沿链路放大：

```
用户语音 →[ASR]→ 文本 →[Speech LLM 意图判断]→ 结构化输出 →[TTS]→ 音频 →[播放]→ 用户
           误识别                 误判/漏判                    音色/断句异常
```

任何一个环节出错，最终体验都是"AI 没听懂我"。所以排查 Bad Case 必须**逐层定位**：问题到底出在 ASR、LLM 还是 TTS？不能只报"语音助手没回应"这种表层症状。

## 2. 三层 Bad Case 分类

### 第 1 层：ASR 层（输入语音 → 文本）

| 类别 | 现象 | 根因 | 本项目实例 | 处理预案 |
|---|---|---|---|---|
| 同音字替换 | 期望"调到"，转写"调倒" | 声学近音、无上下文约束 | 哼唱歌词"调倒睡眠模式" | 领域热词（净化器/新风/睡眠模式）加权；置信度低时让 LLM 二次确认 |
| 尾部丢字 | 期望"…怎么办"，转写"…"就断 | 长句尾部能量弱、静音截断 | demo-4（`wer.js` 内置样本）| VAD 端点检测加尾点；延长录音判定窗 |
| 非语音被转写 | 纯音调/环境噪音被当成字 | 无 VAD 过滤、把音当语 | 440Hz beep → 后端 503 判空 | 前后端判空 + 提示"没听清请重试"（已实现）|
| 噪声/远场 | 有口音、环境声时替换增多 | 采样率/编码/SNR 不足 | 16kHz WAV 为最稳妥目标格式 | 统一 16kHz 单声道；必要时降噪前置 |
| 数字/中英混说 | "PM2.5"、"5G"切分错 | 混合单元未建模 | demo-5 标点丢失 | 评测用音字混合粒度（`wer.js` 的 asr 粒度）单独统计 |

### 第 2 层：Speech LLM 意图判断层（文本 → 结构化输出）

| 类别 | 现象 | 根因 | 处理预案 |
|---|---|---|---|
| 误判在唱歌 | 普通闲聊被当成唱歌并接歌词 | Prompt 对"哼唱"定义过宽 | 收紧判定标准 + 加置信度；仅歌词片段可算，闲聊必须排除 |
| 漏判在唱歌 | 真唱歌被回成普通对话 | ASR 转写后歌词特征丢失 | 多模态线索（语气/音调）+ 给 LLM 更多上下文 |
| 歌名识别错 | 识别成近似歌 | 同曲不同版本/翻唱 | 允许模糊匹配，展示"我觉得是…"降低承诺 |
| 结构化输出失败 | 返回非法 JSON / 字段缺失 | 模型没守格式 | `parseEasterDecision` 容错解析：剥 code block、截 `{…}`（已实现，`mimo-easter.js:25`）|

### 第 3 层：TTS 层（结构化输出 → 音频）

| 类别 | 现象 | 根因 | 本项目实例 | 处理预案 |
|---|---|---|---|---|
| 音色不符 | 唱歌时不像唱歌、像念稿 | 唱歌标签/指令未生效 | 前置 `(唱歌)` 标签 + 显式演唱指令（已实现，`mimo-tts.js:64`）| 播报与唱歌走不同请求构造 |
| 断句/韵律异常 | 接续句换气怪、节拍乱 | 歌词无标点、句子过长 | 接续控制在两句内；保留标点 | 长文本先分段再合成 |
| 播报合成失败 | 回复文字在、没声音 | TTS 不可用/超时/空音频 | `/v1/tts/speak` 返回 503 | 静默降级为仅文字回复（已实现，`synthesizeSpeech` 失败返回 null）|
| 音频播放失败 | 手势未解锁导致不出声 | 浏览器自动播放策略 | 发送手势时解锁 AudioContext（已实现，前端 `play-audio.js`）| 播放失败提示可点开重播 |
| 文本过长被截断 | 长回复只说一半 | TTS 文本长度上限 | `MIMO_TTS_MAX_TEXT_BYTES = 4KB` | 超长回复只播前几句 + 引导查看文字 |

## 3. Bad Case 处置闭环（面试口径）

```
发现 → 归层 → 定根因 → 修一环 → 回归评测 → 沉淀
  ↑                                          │
  └────────────── 持续采集 ──────────────────┘
```

1. **发现**：`wer.js` 按错误率降序输出 Bad Case，先看最高错误率的样本（30%+ 优先）。
2. **归层**：对照上面三层，先确认是 ASR 转写错、LLM 判错、还是 TTS 输出错。转写对的但 LLM 接错 → 不是 ASR 问题。
3. **定根因**：同音字（声学近音）还是噪声（环境）？是 Prompt 边界问题还是模型能力问题？
4. **修一环**：一次只动一层（如只加热词，或只改 Prompt），避免多变量不可归因。
5. **回归评测**：同一批样本重跑 `wer.js`，确认错误率下降且**无回归**（原正确的样本不能变错）。
6. **沉淀**：每个 Bad Case 归档成可复现用例（gold/hyp + 根因 + 修复），进样本集。

## 4. 面试一句话版本

> "Bad Case 分析我会按语音链路的三个环节归层：ASR 转写、Speech LLM 意图判断、TTS 合成。用 CER/WER 指标找出最高错误率的样本，先定位是哪一层的问题，再单点修复并回归同一批样本确保不引入新错误。这个链路闭环我直接在项目里用脚本跑通了，播报和唱歌两条 TTS 分支也都覆盖了。"

## 附：复用本项目测试数据做 Bad Case 的方法

- 单元测试已覆盖"空转写/非 2xx/非法 JSON/空音频"等失败路径（`backend/tests/dashscope-asr.test.js`、`mimo-tts.test.js`、`http-easter.test.js`）——这些本身就是可复现的 Bad Case 用例。
- 想跑真实转写样本：把 `{"gold":"人工期望","hyp":"ASR 实际输出"}` 写进 JSON，`node backend/tools/wer.js samples.json` 即出错误率与对齐明细。
